# DigitalOcean V2 staging runbook

This is a preparation runbook. It creates no DigitalOcean resources and contains no credentials. Keep the existing production app, domain routing, databases, and secrets separate.

## Resource layout

Create a distinct DigitalOcean App Platform app named `securelink-v2-staging` from branch `securelink-v2`, with a staging-only hostname. Run the domain monitor as a separate worker component. Place the app, Managed PostgreSQL, and Managed Valkey in the same region and private network where supported. Do not bind staging to the legacy production database or production mail account.

Use App Platform encrypted secret environment variables for `APP_SECRET_KEY`, `EMAIL_OUTBOX_ENCRYPTION_KEY`, `MFA_ENCRYPTION_KEY`, `DATABASE_URL`, `REDIS_URL`, and SMTP credentials. PostgreSQL URLs must use `sslmode=require` or stronger, and Valkey URLs must use `rediss://`. Set `EXTENSION_REDIRECT_URIS` to the exact Chrome identity callback URI for the extension package being tested. The published extension ID is `dpegeipjmofhdikcbniodhohpckoeole`; the unpacked V2 preview has a different ID, so add its exact callback URI to the isolated staging allowlist after loading the final staging package. Never use wildcard redirect patterns. Set `TRUSTED_PROXY_CIDRS` only to verified ingress proxy CIDRs; leave it empty until the real immediate peer ranges are confirmed. Never trust client-provided forwarding headers by default. Generate separate Fernet keys for email delivery and MFA in each environment and protect both as high-impact secrets. Keep the MFA key stable; losing it makes enrolled TOTP secrets unusable, and rotation requires an explicit re-encryption migration. Use staging-only values. Configure `APP_ENV=staging`, `APP_PUBLIC_URL=https://<staging-host>`, `SMTP_STARTTLS=true`, and a least-privilege database user. Never put secrets in this runbook, app spec, or GitHub commit.

## Deployment sequence

1. Provision isolated API, email-worker, and domain-monitor-worker components, PostgreSQL, and Valkey resources. Run workers as separate long-running components from the same image and give each only the required environment. Restrict database trusted sources to the staging app and authorized admin path; prefer same-region private networking. Restrict the domain-monitor worker's outbound traffic to approved recursive DNS resolvers on UDP/TCP 53 and verify it cannot connect to arbitrary Internet hosts.
2. Add SMTP provider credentials dedicated to staging. Configure a test sender and inbox. Do not deliver staging mail to real users.
3. The API image also serves a minimal same-origin account page and verification/reset pages. Configure the app health check to `/health/ready` and a separate liveness check to `/health/live`.
4. Keep deployment manual while migrations and auth workflows are being exercised. Run `alembic upgrade head` as a single deployment step before shifting traffic; do not run concurrent migrations from every app replica.
5. Confirm the database is on the expected migration revision. Exercise registration, email verification, login, password reset, reset-token replay, the seven-day owner/admin MFA grace and deadline enforcement, MFA enrollment and expiry, one-use-per-step TOTP login and replay rejection, one-time recovery-code use and replay rejection, authenticator rotation with TOTP and recovery code, old-factor rejection, recovery-code replacement and session revocation after rotation, privileged-role MFA disable denial, session revocation after allowed MFA disable, web, extension, and DNS signal provenance, signal and note immutability, tenant-scoped signal listing, URL and non-URL case creation, multi-signal correlation and severity escalation, high/critical auto-case and priority-email enqueue, clean-scan no-case behavior, SPF/DMARC opt-in and opt-out, stable-finding deduplication, recovery signals, transient DNS retry behavior, DNS-only egress, preference auditing, eligible-recipient rules, delivery retry and role/preference recheck, audit provenance, role denial, cross-tenant denial, Redis throttling, and expired access tokens.
6. Exercise authorization with the exact Chrome identity callback of the staging extension package: verify PKCE state/code binding, exact redirect allowlisting, one-time code exchange, 12-hour extension-session expiry, role checks, password-reset revocation, individual extension logout, and rejection of extension tokens on dashboard APIs. The development-branch connector submits manual reviews only and must not replace existing automatic checks. Do not update the published extension until local and staging browser checks plus Chrome/Edge release checks pass.
7. Verify logs omit email action tokens and passwords. Verify 429 behavior and 503 fail-closed behavior when Valkey is unavailable.
8. Restore a PostgreSQL backup into a separate staging cluster and document measured recovery time and data loss window. Managed PostgreSQL provides daily full backups and point-in-time recovery for the prior seven days; validate an actual restore before relying on it.
9. Record deploy commit, migration revision, health status, alert routing, rollback steps, and restore evidence before considering any production promotion.

## Operational gates

- Account-action messages use a transactional encrypted outbox; priority security alerts use a transactional outbox with leases and bounded retries. Alert on oldest pending row, failed rows, and worker health. An SMTP timeout after server acceptance can create duplicate delivery; action links remain single-use. Priority alerts omit URL path/query and make no threat-verdict claim.
- Alert on failed health checks, elevated 5xx/429 rates, database/Valkey unavailability, failed mail delivery, and migration failures.
- Limit SMTP and database credentials to the staging resources; rotate them after staging validation.
- Establish retention and access controls for staging logs and test accounts.
- Confirm the reverse proxy's actual peer ranges and forwarded chain in staging before populating `TRUSTED_PROXY_CIDRS`; verify spoofed forwarding headers cannot change the rate-limit key.
- Maintain an app image/commit rollback procedure and a compatible database migration downgrade or forward-fix plan.
- Assisted MFA recovery after all factors are lost must require two authorized operators, verified account ownership through a pre-established channel, session revocation, an immutable organization audit record, and customer notification. Exercise this process before production; never bypass MFA by making an undocumented database edit.
- No production DNS cutover or production secret reuse is part of this runbook.
